# FAQ

这个文档收口项目中最容易产生误解的设计点、恢复逻辑和使用边界。

## 1. 为什么这个项目不用手机号、邮箱或用户名注册

LINKCONNECT 的目标不是做传统账号体系 IM，而是把“当前设备”当成身份载体。

这样做的收益是：

- 减少身份暴露面
- 避免密码、验证码、找回链路带来的额外复杂度
- 让助记词 / TXT 凭证成为明确的恢复入口

代价也很直接：

- 身份管理更依赖用户自己保管凭证
- 不提供传统云账号那种跨设备自动漫游体验

## 2. 助记词、TXT、恢复码分别是什么关系

- 助记词：给人看的自然语言恢复凭证
- TXT：可下载保存的完整身份凭证文件
- `recovery_code`：程序可直接识别的恢复串

这三者本质上都服务于同一个目的：恢复当前设备身份。

如果你要长期保留身份，最稳妥的方式是同时保存：

- 一份 TXT
- 一份助记词

## 3. 为什么设备指纹不直接用 IP 或浏览器上报信息

因为这些信息既不稳定，也不可信：

- IP 会因为切换网络、VPN、移动网络而变化
- 浏览器环境参数可以被伪造

所以当前实现是：

- 前端上传必要材料
- 服务端基于 `deviceSecret` 派生最终指纹

这样既避免把正常用户卡死在网络变化上，也不把前端上报值当成最终可信身份。

## 4. 为什么群通知不放在系统消息里

因为群更名、成员加入、成员退出、成员被移出、邀请审批，本质都属于该群上下文。

如果这类通知放进系统消息，会产生两个问题：

- 用户无法在群时间线里直接看到状态变化
- 审批、邀请、群成员变更会和真实沟通内容断开

因此现在群相关操作通知默认进入对应群会话，而不是统一塞进系统通知。

## 5. 为什么非群主也能生成邀请链接，但别人加入时还要群主审批

这是故意拆开的两步：

- 生成链接是分发动作，应该尽量轻
- 真正有风险的是“谁将加入这个群”

所以当前策略是：

- 群主生成的链接可以直接用于入群
- 非群主也可以生成链接
- 但通过非群主链接尝试入群时，需要群主审批

这比“生成前审批”更符合实际使用节奏，也更节省群主注意力。

## 6. 为什么重新连接后我会看到离线发件箱

这说明浏览器本地还留有未收到服务端确认的消息。

当前消息状态机是：

- 发送中：已经进入发送流程，但服务端还没确认
- 失败：超过超时或服务端明确返回失败
- 已送达：服务端确认收到
- 已读：对方已读取

连接恢复后，发件箱会尝试自动重发这些未确认消息。如果前置条件不满足，比如群成员资格尚未恢复，消息会继续保留并等待可安全发送的时机。

## 7. 为什么我重新连接后曾经看到群名变成 `grp-*`

这是之前恢复顺序引起的问题：

- 先恢复了群列表
- 后恢复群元数据
- 导致列表里暂时只剩原始群 ID

现在前端已经把群元数据单独持久化，并在恢复时优先还原群名。对已经修复后的会话，这个问题不应再持续出现。

如果你本地仍看到历史遗留的 `grp-*`，通常意味着：

- 这条本地缓存来自旧版本
- 或这次会话还没重新拿到该群的正式元数据

## 8. 为什么群成员重连后会提示 `NOT_IN_GROUP`

这不是“加密密钥丢了”，而是“当前连接上的群成员资格还没恢复完成”。

现在的修复方向是：

- 普通群成员关系持久化
- 设备重连并重新绑定后自动恢复群关系
- 离线审批结果支持重连补发
- 发件箱在成员状态未恢复前不会盲目重发

如果某个群是非常早期的历史遗留群，且当时没有落下完整成员记录，那么它可能需要一次重新通过有效邀请链接入群，之后就会稳定。

## 9. 为什么陌生人私聊只能先发一条

这是产品刻意保留的限制，不是 Bug。

目的有两个：

- 减少陌生设备持续骚扰
- 保持“联系人关系”在私聊权限中的实际作用

一旦对方回复，或者双方已经建立联系人关系，这个限制就会解除。

## 10. 为什么 README 里没有把所有细节都写完

README 负责说明：

- 项目是什么
- 主要能力边界是什么
- 怎么启动和部署
- 为什么这样设计

它不适合承载所有协议细节和问题排查内容。随着项目继续演进，后续更合理的结构会是：

- `README.md`：项目总览
- `docs/FAQ.md`：高频问题
- `docs/ARCHITECTURE.md`：更细的系统架构
- `docs/PROTOCOL.md`：协议与状态机
